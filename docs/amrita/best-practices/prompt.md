# 提示词设计实践

AmritaBot 的提示词分两层：框架负责的**协议层**，和用户可编辑的**角色层**。大多数「模型不听话」的问题，不是角色写得不够长，而是两层互相打架，或者把工具、技能该做的事塞进了提示词。

本文讲怎么写角色层，以及怎么和协议层配合。

## 1. 先分清两层

框架会在角色提示词之前拼一段固定结构：

```text
<SCHEMA>
...输出约束、用户消息格式说明...
</SCHEMA>

<SYSTEM_INSTRUCTIONS>
你的角色提示词
</SYSTEM_INSTRUCTIONS>

<SUMMARY>
...压缩后的历史摘要（如果开启 compact）...
</SUMMARY>
```

角色提示词之后还可能拼接：

- `<EXTRA>`：用户的额外规则（`allow_custom_prompt = true` 时）；
- 技能使用指引：启用的技能名、描述与调用方式；
- 工具 schema：由模型接口层提供，不在提示词文本里。

所以角色层不要重复写「你是 AI」「回答要自然」「不要输出 Markdown」这类框架已经约束的内容。重复不会加强，只会占用预算、制造冲突。

## 2. 角色提示词写什么

一份可用的角色提示词通常包含五块：

1. **身份**：你是谁，服务谁，边界在哪；
2. **目标**：你主要帮用户完成什么；
3. **风格**：语气、长度、称呼、是否用表情；
4. **工具与技能策略**：什么时候查资料、什么时候打开技能、什么时候直接回答；
5. **禁止项**：不能做什么，遇到什么要拒绝或转交。

示例：

```text
你是 Amrita，一个面向技术团队的中文助手。你说话简洁、直接，先给结论再解释。

你的主要任务：
- 回答部署、配置和插件开发问题；
- 帮用户排查报错，必要时调用工具查日志或文档；
- 不确定时明确说「我不确定」，不要编造版本号或配置项。

风格：
- 默认 3-6 句，复杂问题用短列表；
- 不使用「亲」「宝子」这类称呼；
- 代码放在代码块里，命令标明执行目录。

边界：
- 不提供绕过权限、攻击他人系统的步骤；
- 涉及账号、密钥、隐私数据时，提醒用户脱敏。
```

不需要写成几百行。角色越短、越具体，模型越容易稳定执行。

## 3. 群聊与私聊分开写

群聊和私聊的上下文结构不同，提示词也应该不同。

### 群聊

群聊里模型看到的是多个人的消息，每条带角色、昵称、QQ 号和时间。提示词要解决：

- 当前该不该接话，接谁的话；
- 多个人同时提问时先回答谁；
- 不要假设所有消息都来自同一个人；
- 不要复述群成员的长消息；
- 涉及群规则时以管理员为准。

示例片段：

```text
你在一个技术群里。用户消息会以 <msg role="..." name="..." uid="..."> 的形式给出。
只回应与你相关的提问或讨论，不要对每条消息都接话。
如果多人同时提问，先回答最近一次 @ 你或明确向你提问的人。
不确定对方在叫谁时，不要抢答。
```

### 私聊

私聊是一对一，提示词可以更个性化：

- 记住用户的称呼与偏好（长期记忆插件会提供 memo，不需要在提示词里硬编码）；
- 允许更长的解释；
- 可以直接追问澄清。

不要把群聊的「不要抢话」搬到私聊，也不要让私聊提示词假设有第三个人在场。

## 4. 占位符与自动注入

角色提示词里可以使用以下占位符，框架在发送前替换：

| 占位符 | 替换为 |
| --- | --- |
| `{self_id}` | Bot 的 QQ 号 |
| `{user_id}` | 当前用户 QQ 号 |
| `{user_name}` | 当前用户昵称 |

没有 `${环境变量名}` 这种提示词内插值。需要把环境变量写进提示词时，在部署时生成模板文件，或通过配置/插件注入，不要指望框架替换。

Cookie 反注入也不需要手写 `{cookie}`。开启 `core.cookie.enable_cookie` 后，框架会在 `<SCHEMA>` 里自动注入一段 `<HIDDEN>` 标记，并在输出侧检测泄露。角色提示词里不用、也不应该重复这个值。

## 5. 不要和消息格式打架

`function.message_type = "xml"` 时，用户消息会被包装成：

```xml
<msg role="群主" name="张三" uid="12345" time="2026-09-19 Saturday 15:24:37">
消息内容
</msg>
```

引用消息会多一层 `<ref name="..." uid="...">...</ref>`。

角色提示词要做的，是告诉模型**怎么理解**这些标签，而不是让模型**输出**这些标签。比如：

```text
用户消息中的 <msg> 标签只用于区分说话人，你的回复不要包含 <msg>、<ref> 或任何 XML 标签。
```

如果提示词里写「请用 XML 格式回复」，模型可能会把整段回答包进标签，前端或适配器再解析时就会出问题。

`message_type = "legacy"` 时消息是紧凑的文本格式，更省 token，但多人对话时说话人容易混。群聊建议 `xml`，私聊或成本敏感场景可以用 `legacy`。

## 6. 工具与技能要「指路」，不要「代劳」

提示词不应该教模型具体怎么调工具，工具 schema 已经写了参数。提示词只需要回答：

- 什么情况下该用工具；
- 什么情况下不该用；
- 工具失败后怎么办；
- 技能和工具的分工。

示例：

```text
当用户询问当前部署状态、日志或版本时，先调用工具查证，不要凭记忆回答。
如果工具返回错误，把错误原样告诉用户，并给出下一步排查建议；不要假装查询成功。
当任务匹配某个技能的描述时，先用 skill_open 读取技能正文，再按正文执行；不要凭技能名猜测步骤。
```

不要写「你必须调用 read_memory 工具，参数 query 填用户原话」——参数 schema 已经约束了，提示词再写一遍容易和工具描述冲突。

## 7. 控制长度与稳定性

- **系统提示越稳定，前缀缓存越容易命中**。不要把当前时间、随机数、每次变化的状态写进角色提示词；这些应该由框架的上下文或工具提供。
- **不要把历史摘要复制进提示词**。`compact` 策略会自动加 `<SUMMARY>`。
- **不要把长期记忆全文塞进提示词**。L1 备忘录由插件注入，L2 按需检索。
- **示例只保留最能说明问题的 1–2 个**。大量 few-shot 会挤占上下文，也容易让模型机械模仿。
- **不要写「永远」「绝对」这类无法执行的规则**。模型做不到绝对，反而会在冲突时忽略整段。

## 8. 模板管理与迭代

提示词模板位于 chat 插件的配置目录：

```text
<localstore 配置目录>/chat/
├── group_prompts/
│   └── default.txt
└── private_prompts/
    └── default.txt
```

具体路径可以用 `ambot nb localstore` 查看，或在 WebUI 的「提示词预设」页面直接编辑。切换模板用 `/prompt template group|private <名称>`，1.12 起该操作要求超级管理员。

![群聊与私聊提示词模板](/webui/prompts.png)

迭代建议：

1. 先写一个最小版本，跑 10–20 条真实对话；
2. 记录失败类型：没接话、答非所问、太长、编造、工具没调；
3. 一次只改一类问题，比如只改「群聊接话规则」；
4. 保留旧版本，出问题能回滚；
5. 用不同模板做 A/B，不要在同一份模板上反复叠加补丁。

## 9. 常见反模式

| 反模式 | 后果 | 改法 |
| --- | --- | --- |
| 把工具参数写进提示词 | 与 schema 冲突，模型照抄错误格式 | 只写「何时用」，参数交给 schema |
| 写「请用 XML 回复」 | 回复被标签包裹，解析异常 | 明确「不要输出 XML 标签」 |
| 在提示词里手写 cookie | 重复注入，泄露风险 | 交给 `core.cookie` 自动处理 |
| 群聊提示词假设只有一个用户 | 张冠李戴，答错人 | 用 `<msg>` 的 name/uid 区分 |
| 用几百行 few-shot 堆风格 | 上下文膨胀，风格僵化 | 保留 1–2 个代表性例子 |
| 把长期记忆全文粘进提示词 | 每轮成本高，信息过时 | 用记忆插件的 memo 与检索 |
| 提示词要求「必须调用工具」 | 简单问题也绕一圈，延迟高 | 写清触发条件，允许直接回答 |
| 角色提示与技能正文冲突 | 模型在两套规则间摇摆 | 技能负责流程，角色只写边界与风格 |

## 10. 检查清单

- ☐ 角色提示词没有重复框架已有的格式约束
- ☐ 群聊/私聊使用不同模板
- ☐ 只使用受支持的占位符，没有 `${ENV}` 或手写 `{cookie}`
- ☐ 没有要求模型输出 `<msg>` / `<ref>` 等协议标签
- ☐ 工具与技能只写「何时用」，不写参数细节
- ☐ 提示词里没有当前时间、随机状态等每轮变化的内容
- ☐ 长度控制在模型能稳定执行的范围，示例不超过 2 个
- ☐ 改完用真实对话验证，并保留可回滚的旧版本
