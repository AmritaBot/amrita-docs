# 编写有效的 Skills

Skill 不是「更长的提示词」，也不是「换一种写法的工具」。它适合封装一类需要按步骤执行、需要参考材料、可能附带脚本的可复用工作流。写得好，模型只在需要时加载正文与资料；写得差，它会变成一段又长又模糊、永远不会被正确触发的说明。

本文讲怎么写一个能被模型正确选中、正确执行、容易维护的 Skill。运行与配置见[Skills 接入](../features/chat/skills.md)。

## 1. 先判断该不该写成 Skill

| 需求 | 更合适的形式 |
| --- | --- |
| 固定角色、语气、边界 | 提示词模板 |
| 一次 API 调用、一次查询 | Tool |
| 多步流程 + 参考资料 + 可选脚本 | **Skill** |
| 只需要在系统提示里加一段规则 | `extra_prompt` 或提示词 |

判断标准很简单：如果模型需要「先读一段说明，再按步骤做，中间可能查文件或跑脚本」，就写成 Skill；如果只是一个原子能力，写成 Tool。

## 2. 目录结构

```text
config/chat/skills/
└── weekly-report/
    ├── SKILL.md
    ├── references/
    │   ├── format.md
    │   └── examples.md
    ├── assets/
    │   └── template.md
    └── scripts/
        └── collect.py
```

- `SKILL.md`：入口，必须有；
- `references/`：详细资料、规范、长示例，按需读取；
- `assets/`：模板、静态文件；
- `scripts/`：可执行脚本，开启 `allow_script_execution` 后才会注入。

目录名建议用短横线小写，和 `name` 保持一致。脚本文件名会成为工具名的一部分，避免大写、空格和特殊字符。

## 3. `SKILL.md` 的组成

```markdown
---
name: weekly-report
description: 根据用户提供的项目列表与本周进展，生成结构化周报。用户要求写周报、汇总本周工作、整理项目进度时使用。
version: 1.0.0
---

# 目标

把用户提供的零散进展整理成一份可直接发送的周报。

# 输入

- 项目名称与本周完成事项；
- 风险、阻塞、下周计划（可选）。

如果用户没有提供项目列表，先追问，不要假设。

# 步骤

1. 按项目分组，合并重复事项；
2. 每个项目保留「完成 / 进行中 / 风险」三类；
3. 生成「本周概览 → 分项目进展 → 风险与下周计划」；
4. 输出前检查是否遗漏用户明确提到的风险。

# 输出格式

使用 Markdown 标题与短列表。总长度控制在 600 字以内。

# 失败处理

信息不足时只输出已确认的部分，并列出需要用户补充的字段；不要编造进度。

用户请求：
$ARGUMENTS
```

### 3.1 frontmatter

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 唯一标识，也是工具名的一部分。用小写字母、数字、短横线 |
| `description` | 是 | 模型判断「何时打开」的唯一依据，最重要 |
| `version` | 否 | 便于自己维护，不参与触发判断 |

不要塞自定义字段指望框架读取。当前只保证这三个字段的语义，其他字段可能被忽略。

### 3.2 `description` 决定触发率

`description` 要同时写清「做什么」和「什么时候用」，最好再带一个排除条件。

不推荐：

```yaml
description: 周报助手
```

推荐：

```yaml
description: 根据项目列表与本周进展生成结构化周报。用户要求写周报、汇总本周工作、整理项目进度时使用；单纯查询某个任务状态时不要使用。
```

一个实用的写法：

```text
<能力>。用户<触发场景 1>、<触发场景 2>、<触发场景 3>时使用；<不适用场景>时不要使用。
```

触发场景用用户真实会说的话，不要用内部术语。比如用户会说「帮我写个周报」，不会说「执行 weekly report generation pipeline」。

### 3.3 正文只写「怎么做」

正文是给模型执行的流程，不是给人看的介绍。建议按固定小标题组织：

- **目标**：一句话说明产出；
- **输入**：需要哪些信息，缺了怎么办；
- **步骤**：编号列表，每步一个动作；
- **输出格式**：结构、长度、语言；
- **失败处理**：信息不足、工具失败、格式不符时怎么办。

这样模型打开技能后能快速定位，`skill_open` 的 `section` 参数也可以按标题只加载某一部分。

### 3.4 `$ARGUMENTS`

`skill_open` 的 `arguments` 参数会替换正文中的 `$ARGUMENTS`。把用户请求放在正文末尾或「输入」一节，不要让模型自己猜。

如果技能不需要用户原文，可以省略 `$ARGUMENTS`，但要在正文里说明输入从哪来。

## 4. 渐进披露：正文当索引，资料放文件

`mode = "progressive"` 时，模型先看到技能名与 description，调用 `skill_open` 才加载正文，正文里提到支持文件时再用 `skill_read` 按相对路径读取。

这意味着：

- `SKILL.md` 保持短，建议 100–200 行以内；
- 长规范、格式手册、大量示例放 `references/`；
- 正文里明确写「需要详细字段说明时，用 skill_read 读取 references/format.md」；
- 不要把整个规范复制进 `SKILL.md`，否则每次打开都付一遍 token。

示例：

```markdown
字段定义与校验规则见 `references/format.md`。
需要完整示例时读取 `references/examples.md` 的「完整周报」一节。
```

`skill_read` 支持 `start_line` / `end_line`，长文件可以分段读。给文件起清晰的名字，比让模型猜路径更重要。

## 5. 脚本：把确定性操作交给代码

适合写成脚本的：

- 解析固定格式文件；
- 调用外部 API 并整理结果；
- 生成图表、压缩图片、转换格式；
- 需要精确计算或校验的逻辑。

不适合写成脚本的：

- 需要模型判断的写作、总结、分类；
- 需要多轮交互的流程；
- 依赖用户上下文、但脚本拿不到的东西。

### 5.1 脚本契约

- 支持 `.py` / `.sh` / `.js` / `.rb` / `.pl` / `.ps1` 等；
- 参数以 **JSON 从 stdin 传入**，不是命令行参数；
- 工作目录是技能根目录；
- 脚本名会成为工具名的一部分，格式为 `技能名__脚本名`；
- 第一个注释块或 Python docstring 会作为工具描述，写清用途与参数；
- 输出尽量短，结构化（JSON 或纯文本），不要把调试日志混进 stdout。

Python 示例：

```python
"""收集指定项目的本周提交并返回 JSON。

stdin: {"project": "amrita", "since": "2026-11-01"}
stdout: {"commits": [{"hash": "...", "title": "..."}]}
"""

import json
import sys

payload = json.load(sys.stdin)
project = payload["project"]
since = payload.get("since", "")

# ... 查询逻辑 ...

print(json.dumps({"commits": []}, ensure_ascii=False))
```

### 5.2 脚本安全

- 不要读取与技能无关的绝对路径；
- 不要硬编码密钥，从环境变量或配置读取；
- 不要执行用户传入的任意命令；
- 输出前做大小限制，避免把整库数据塞回模型；
- 失败时返回非零退出码和可读错误，不要静默成功。

`allow_script_execution = false` 时脚本不会注入，技能只返回正文。远程沙箱场景还应关闭 `echo_skill_directory`，避免暴露本机路径。

## 6. 触发与选择

- `all_skills = true` 时所有技能都参与选择；技能很多时，description 之间会互相竞争。
- `all_skills = false` 时只启用 `selected` 里的技能。生产环境建议按场景白名单，避免无关技能被误触发。
- 技能不是越多越好。一个机器人同时启用 20 个技能，模型在 description 之间做选择的难度会明显上升。
- 技能之间不要写重叠的触发场景。比如「写周报」和「汇总工作」如果 description 几乎一样，模型会随机选一个。

## 7. 测试 Skill

### 7.1 静态检查

- `name` 是否符合命名规则；
- `description` 是否包含触发场景与排除场景；
- 正文是否有明确输入、步骤、输出、失败处理；
- 引用的 `references/` 文件是否真实存在；
- 脚本是否有可执行权限、能否独立跑通。

启动后可在 WebUI 的「技能管理」看到校验状态；失败项会显示 `error` 原因。

### 7.2 触发测试

准备三组句子：

1. **应该触发**：用户真实会说的 5 种表达；
2. **不应该触发**：语义相近但应交给别的技能/工具/直接回答的 5 种表达；
3. **边界**：信息不完整、语言混用、带引用消息的情况。

观察 `meta.skill_trigger` 打开时的「使用了技能：xxx」通知，确认模型是打开了正确的技能，而不是碰巧答对。

### 7.3 执行测试

- 信息完整时，输出是否符合格式；
- 信息缺失时，是否会追问而不是编造；
- 脚本失败时，是否把错误告诉用户；
- 长参考文件是否按需读取，而不是一次性全读；
- 多轮对话中，技能是否会被重复打开。

## 8. 常见反模式

| 反模式 | 后果 | 改法 |
| --- | --- | --- |
| `description` 只写「XX 助手」 | 模型不知道何时用，永不触发 | 写清触发场景与排除场景 |
| `SKILL.md` 几百行 | 每次打开都贵，模型抓不住重点 | 正文当索引，细节放 `references/` |
| 正文写「你可以自行决定步骤」 | 行为不稳定 | 给编号步骤与输出格式 |
| 和系统提示冲突 | 模型在两套规则间摇摆 | 技能只写流程，角色边界放提示词 |
| 脚本把日志打到 stdout | 模型把日志当结果 | 日志走 stderr，stdout 只放结果 |
| 脚本参数从 argv 取 | 与框架契约不符，拿不到参数 | 从 stdin 读 JSON |
| 一个技能塞多个无关任务 | 触发范围模糊，输出混杂 | 拆成多个技能，或加 `section` |
| 技能名与脚本名带大写/空格 | 工具名不合法，注入失败 | 小写、短横线、下划线 |
| 依赖本机绝对路径 | 换环境就坏 | 用技能根目录相对路径 |

## 9. 检查清单

- ☐ 这个需求确实需要多步流程，而不是一个 Tool 或一段提示词
- ☐ `name` 合法且与目录名一致
- ☐ `description` 写清「做什么 + 何时用 + 何时不用」
- ☐ 正文有目标、输入、步骤、输出格式、失败处理
- ☐ `$ARGUMENTS` 放在正确位置，或明确说明不需要
- ☐ 长内容在 `references/`，正文只留索引
- ☐ 脚本从 stdin 读 JSON，stdout 只输出结果
- ☐ 脚本不依赖绝对路径、不硬编码密钥
- ☐ 只启用当前场景需要的技能
- ☐ 测过应触发、不应触发、信息缺失三类输入

Skill 的质量，最终体现在「模型能不能在正确的时机打开它，并按里面的步骤稳定做完」。先把这三件事做好，再考虑加脚本、加资料、加示例。
